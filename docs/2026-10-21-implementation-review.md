## 1. 오늘의 결론과 현재 위치

### 1.1 지금 완성한 것은 모델이 아니라 모델을 위한 데이터 준비 과정이다

우리는 다음 문제를 풀기 위한 기반을 만들었다.

> 특정 관측소에서 예측 기준시각 `t`까지의 관측을 보고, 같은 관측소의 **정확히 `t + 6시간` 유의파고**를 예측한다.

이것은 연속적인 수치, 예를 들어 `0.6m`, `1.2m`를 예측하는 **회귀 문제**다.

현재까지 구현한 것은 다음이다.

```text
CSV 읽기·검사·정규화
→ 처리 결과와 출처 기록 저장
→ 정제 데이터 재로딩
→ 현재값·과거값·변화량 생성
→ 실제 6시간 뒤 관측을 정답으로 연결
→ 필요한 값이 모두 있는 표본 선택
→ 학습 / 검증 / 테스트 구간 분리
→ 이 코드들이 의도대로 작동하는지 테스트
```

아직 모델을 `fit()`해서 학습하거나, 예측값으로 MAE·RMSE를 계산하지 않았다.
따라서 현재 단계에서 “모델의 예측 정확도가 좋다”고 말할 수는 없다.

### 1.2 학습용 데이터셋을 만든다는 뜻

원본 관측 한 행은 다음과 같은 의미다.

```text
관측소 22101에서 2025-01-01 06:00에 파고 0.5m, 풍속 4.7m/s가 관측되었다.
```

학습용 표본 한 행은 다음과 같은 의미다.

```text
06:00까지 알 수 있었던 입력 정보 X
→ 실제 12:00의 유의파고 y
```

즉, 과거 데이터를 이용해 **문제와 정답의 쌍**을 만든 것이다.

학습할 때는 여러 쌍으로 관계를 배우고, 실제 예측할 때는 새로운 `X`만 전달한다.
실시간 예측 시점에는 미래 정답 `y`가 아직 없다.

### 1.3 현재 위치

```text
A: 환경·문제 정의
→ B: CSV 정규화·검사·저장
→ C1~C6: 학습용 표본 생성·시간 분할
→ C7: 코드 검증 완료   ← 현재 위치
→ D: 기준 모델·머신러닝 학습 및 성능 비교
→ 저장한 모델을 사용하는 API
→ 배포·시연·한계 정리
```

이 문서에서 B 단계는 C를 이해하는 데 필요한 선행 작업으로 함께 복습한다.
모든 B 작업이 오늘 처음 시작된 것은 아니다. 초기 샘플 검토와 데이터 명세는 이전에 작성되었고,
오늘 커밋에는 정규화 보완, 범위·중복 검사, 준비 CLI, C 단계 및 테스트가 포함되어 있다.

### 2.2 열 수가 달라지는 이유

| 단계                  | 구성                                               | 열 수 |
| --------------------- | -------------------------------------------------- | ----: |
| 관측 표               | 식별 정보 2개 + 관측 수치 8개                      |    10 |
| 특성 표               | 식별 정보 2개 + 모델 입력 특성 7개                 |     9 |
| 정답 연결 표          | 식별 정보 2개 + 정답시각 1개 + 입력 7개 + 정답 1개 |    11 |
| 완전한 표본·분할 결과 | 위 11열 중 행만 선택                               |    11 |

“관측에서 특성을 만들었는데 왜 열 수가 줄지?”라고 생각할 수 있다.
원본 10열을 전부 유지하면서 더하는 것이 아니라, 현재 버전에서 필요한 관측값만 선택하고 과거 특성을 추가하기 때문이다.

### 2.3 두 종류의 결측을 구분한다

1. **행은 있는데 셀이 비어 있음**: 어떤 시각의 유의파고가 `pd.NA`다.
2. **그 시각의 행 자체가 없음**: 예를 들어 07시 다음이 09시이고 08시 행이 없다.

`df.isna().sum()`은 첫 번째를 센다. 두 번째는 시간축과 관측시각을 비교해야 찾을 수 있다.

현재 연간 파일은 2025년의 매시간 8,760개 시각 중 8,043개 시각을 포함한다.
파일에 없는 시각은 717개다. 이 사실만으로 장비 고장이나 누락 원인을 확정하지는 않는다.

특성을 만들 때는 두 번째도 중요하다. 과거 시각 행이 없으면 `merge()` 결과의 과거값이 결측이 된다.

### 2.4 시간대에 관한 중요한 전제

현재 정제 파일 이름은 `buoy_22101_2025_utc_assumed.csv`다.

```json
{
  "source_timezone": "UTC",
  "source_timezone_status": "caller_supplied_unverified",
  "output_timezone": "UTC"
}
```

이는 **원본 CSV가 UTC임을 확인했다는 뜻이 아니다.**
현재는 호출자가 원본 시각을 UTC라고 가정해 처리했고, 그 가정이 미확인임을 기록했다.
이 문서의 실제 데이터 시각도 그 가정을 유지한 내부 UTC 표현이다.

원본이 KST라는 근거가 확인되면 원본에서 다시 정제하고 데이터셋과 분할도 다시 만들어야 한다.
메타데이터의 상태 문자열만 `confirmed`로 고쳐서 사실처럼 만드는 것은 해결이 아니다.

## 4. B 단계: CSV 읽기와 정규화

### 4.1 해결하려는 문제

CSV는 숫자·날짜처럼 보여도 본질적으로는 텍스트다.
한글 헤더, `.5` 같은 숫자 표기, 빈 셀, 시간대 없는 시각을 코드가 일관되게 해석해야 한다.

여기서는 **원본을 읽는 일**과 **내부 규칙에 맞게 변환하는 일**을 나눴다.

```text
파일 경로·인코딩
→ read_buoy_csv(): 원본 문자열 표
→ normalize_buoy_data(): 내부 관측 표
```

### 4.2 `read_buoy_csv()`의 입력과 출력

```python
raw = read_buoy_csv(
    "data/preview/OBS_BUOY_TIM_20261021192756.csv",
    encoding="cp949",
)
```

- 입력: CSV 경로 `str | Path`, 인코딩 문자열.
- 출력: `pd.DataFrame`. 이 단계에서는 `dtype="string"`으로 원본 셀을 읽는다.
- 실패: 파일 없음, 인코딩 오류, 잘못된 CSV 구조, 필수 열 누락, 데이터 행 없음 등.

주요 옵션의 이유:

| 옵션                       | 이유                                                   |
| -------------------------- | ------------------------------------------------------ |
| `encoding_errors="strict"` | 읽을 수 없는 바이트를 대체 문자로 숨기지 않는다.       |
| `dtype="string"`           | 지점번호와 원본 숫자·시각 표기를 먼저 보존한다.        |
| `keep_default_na=False`    | `NA`, `NaN` 같은 문자열을 임의로 결측 처리하지 않는다. |
| `skip_blank_lines=False`   | 빈 레코드를 조용히 건너뛰지 않는다.                    |
| `on_bad_lines="error"`     | 파서가 잘못된 줄로 판단한 입력을 조용히 버리지 않는다. |

이 옵션들이 모든 가능한 CSV 손상을 완벽히 잡는다는 뜻은 아니다.
기본 파싱 뒤에도 필수 열·값·형식 검사가 필요한 이유다.

### 4.3 `normalize_buoy_data()`의 입력과 출력

```python
observations = normalize_buoy_data(
    raw,
    source_timezone="UTC",  # 현재 연간 실험의 미확인 가정
    source_name="연간 부이 원본 CSV",
)
```

- 입력: 원본 DataFrame, 해석에 사용할 원본 시간대, 오류 보고용 출처 이름.
- 출력: 내부 이름 10열과 지정한 자료형을 가진 새 DataFrame.
- 원본 DataFrame은 복사해 사용한다.
- 행을 임의 보간하거나 누락 시각을 생성하지 않는다.

정상 흐름:

```text
필수 열·행 확인
→ 시간대 이름 확인
→ 문자열 양끝 공백 제거
→ 지점·일시 필수 값 확인
→ 날짜 형식 및 실제 날짜 확인
→ 시간대 부여 후 UTC 변환
→ 수치 변환과 빈 값 구분
→ 범위·중복 검사
→ 열 순서 통일·정렬
→ 부가정보를 붙여 반환
```

### 4.4 실제 셀은 어떻게 바뀌는가

| 원본 셀·열          | 변환 결과        | 이유                                     |
| ------------------- | ---------------- | ---------------------------------------- |
| 지점 `"22101"`      | 문자열 `"22101"` | 수치 계산 대상이 아니라 식별자다.        |
| 가상 지점 `"00123"` | 문자열 `"00123"` | 정수 변환으로 앞자리 0을 잃지 않는다.    |
| 유의파고 `".5"`     | 실수 `0.5`       | 소수점 앞의 0이 없어도 숫자로 해석된다.  |
| 풍속 `" 4.3 "`      | 실수 `4.3`       | 앞뒤 공백 제거 후 변환한다.              |
| 유의파고 빈 문자열  | `pd.NA`          | 값이 없음을 보존한다.                    |
| 유의파고 `"0"`      | 실수 `0.0`       | 0은 빈 값이 아니다.                      |
| 유의파고 `"abc"`    | `ValueError`     | 숫자가 아닌 잘못된 입력을 숨기지 않는다. |
| 수치 `"inf"`        | `ValueError`     | 무한대는 관측 수치로 사용하지 않는다.    |

선택 관측 열이 통째로 없으면 대응 내부 열을 `Float64`의 `pd.NA`로 생성한다.
단, `지점`, `일시`, `유의파고(m)` 열 자체는 필수다.
유의파고 **열이 있어야 한다는 규칙**과 각 셀에 **항상 값이 있어야 한다는 규칙**은 다르다.

### 4.5 `errors="coerce"`를 쓰면서도 오류를 숨기지 않는 방법

핵심 로직을 축약하면 다음과 같다.

```python
# 원래 비어 있던 위치를 먼저 기록한다.
blank_mask = values.isna() | values.eq("")

# 숫자로 바꾸지 못한 값은 일단 결측으로 표시한다.
numeric = pd.to_numeric(values.mask(blank_mask), errors="coerce").astype("Float64")

# 원래 비어 있지 않았는데 변환 후 결측이면 입력 오류다.
invalid_mask = (~blank_mask & numeric.isna()) | numeric.isin(
    [float("inf"), float("-inf")]
)
```

예를 들어 `values = [".5", "", "abc"]`라면:

```text
blank_mask:   [False, True,  False]
numeric:      [0.5,   <NA>,  <NA>]
invalid_mask: [False, False, True]
```

빈 셀과 변환 실패가 모두 `pd.NA`로 보일 수 있으므로 **변환 전 상태를 함께 기억**하는 것이다.

### 4.6 시각 문자열에 시간대를 부여하는 것과 변환하는 것

설명용 예시이며 원본 CSV의 시간대를 확정하는 예가 아니다.

```python
# 시간대 없는 09시를 한국 시각이라고 해석한다.
localized = pd.Timestamp("2025-01-01 09:00").tz_localize("Asia/Seoul")

# 같은 순간을 UTC로 표현한다.
converted = localized.tz_convert("UTC")
```

```text
시간대 없음: 2025-01-01 09:00
KST 부여:   2025-01-01 09:00+09:00
UTC 변환:   2025-01-01 00:00+00:00
```

- `tz_localize()`는 시간대 없는 시각을 **어느 지역의 시각으로 해석할지 부여**한다.
- `tz_convert()`는 이미 시간대가 있는 동일한 순간을 다른 시간대로 **표현**한다.

처음 해석한 시간대가 틀리면 뒤의 UTC 변환 코드가 정상이어도 실제 시각은 틀릴 수 있다.

### 4.7 인코딩 문제는 데이터 값 손상과 구분한다

이전에 편집기에서 한글 헤더가 깨져 보였지만 다음 명령으로 정상 해독을 확인했다.

```bash
iconv -f CP949 -t UTF-8 data/raw/buoy_sample.csv | head -n 2
```

이 명령은 변환한 문자열을 파이프로 출력할 뿐, 새 파일을 저장하지 않는다.
프로젝트 폴더에 파일이 생기지 않는 것이 정상이다.
또한 CP949 파일을 `preview` 폴더에 넣는 것만으로 UTF-8이 되지는 않는다.

지금 해결 방식은 편집기의 표시 상태에 의존하지 않고, 로더에 인코딩을 명시하고 원본은 보존하는 것이다.

## 5. B 단계: 범위·중복 검사와 재현 가능한 저장

### 5.1 B3 범위·중복 검사: 숫자로 읽힌다고 정상 관측은 아니다

숫자 변환이 성공해도 풍속 `-1`이나 습도 `150`은 기본 규칙에 맞지 않는다.

현재 기본 범위 규칙은 다음과 같다.

| 항목                   | 검사                          |
| ---------------------- | ----------------------------- |
| 풍속·유의파고·평균파고 | 0 이상                        |
| 습도                   | 0 이상 100 이하               |
| 풍향                   | 0 이상 360 이하               |
| 현지기압               | 0보다 큼                      |
| 기온·수온              | 유한한 숫자, 음수 자체는 허용 |

이것은 **기본 형식·범위 검사**다. 센서의 교정 상태나 공식 품질 판정까지 보장하지 않는다.
현재 파일의 최댓값을 허용 상한으로 쓰지도 않는다.

중복 검사는 다음 기준이다.

```python
duplicate_mask = result.duplicated(
    subset=["station_id", "observed_at"],
    keep=False,
)
```

같은 관측소·같은 시각에 두 관측이 있으면, 임의로 첫 번째 값을 쓰지 않고 오류를 낸다.
`keep=False`는 중복 그룹의 첫 번째 행도 함께 표시한다.
검사가 끝나면 `(station_id, observed_at)` 순서로 정렬한다.

### 5.2 오류 보고용 `_reject_invalid_values()`

입력은 원본 표, 검사 열, 오류 마스크, 출처, 오류 이유다. 정상이면 `None`을 반환하고,
오류가 있으면 첫 오류의 위치·원본 값·이유를 포함한 `ValueError`를 발생시킨다.

```text
오류 마스크
→ 미확정 마스크 값을 False로 정리
→ True가 하나라도 있는지 확인
→ 첫 True의 행 라벨 선택
→ 원본 셀과 레코드 위치 조회
→ ValueError
```

“첫 번째만 검사한다”는 뜻이 아니다.
마스크 계산으로 해당 열 전체를 검사한 다음, **보고할 오류 하나를 선택해 실행을 멈추는 것**이다.
앞선 열에서 예외가 발생하면 이후 열 검사는 진행되지 않는다.

### 5.3 B5 `prepare_data()`의 역할

파일: [prepare_data.py](/Users/jake/Documents/data-project/scripts/prepare_data.py)

```python
metadata = prepare_data(
    input_path,
    output_path,
    encoding="cp949",
    source_timezone="UTC",
)
```

- 입력: 원본 경로·새 출력 경로·인코딩·원본 시간대 해석값.
- 반환: 처리 기록 `dict[str, object]`.
- 파일 출력: UTF-8 CSV와 같은 이름의 `.metadata.json` 두 파일.
- 정상 종료 시 CLI의 `main()`은 운영체제에 종료 코드 `0`을 전달한다.
- 예상 가능한 입력·저장 오류는 stderr에 보고하고 종료 코드 `1`을 반환한다.

흐름:

```text
경로 검증·기존 출력 존재 검사
→ 원본 SHA-256 계산
→ 읽기·정규화
→ 원본 SHA-256 재확인
→ 처리 기록 구성
→ 새 CSV 생성
→ 새 JSON 생성
→ 기록 반환
```

### 5.4 왜 CSV만 저장하지 않고 JSON도 저장했는가

CSV에는 DataFrame의 자료형과 `attrs`가 자동으로 보존되지 않는다.
내일 다시 읽으면 지점번호가 정수로, 시각이 문자열로 바뀔 수 있다.
또한 “어느 파일을 어떤 인코딩과 시간대 가정으로 처리했는가”도 CSV만으로 알기 어렵다.

따라서 JSON에 다음을 기록했다.

- 원본 경로, SHA-256, 인코딩.
- 원본 시간대 해석값과 미확인 상태.
- 출력 시간대, 출력 경로.
- 행 수, 열 이름, 자료형, 열별 결측 수.
- 처음·마지막 관측시각, 매핑되지 않은 추가 열.

SHA-256은 파일 바이트를 식별하는 지문이다. 지문이 같다는 것은 검사한 파일 바이트가 같다는 뜻이지,
그 데이터가 실제 바다 상태를 정확히 측정했다는 뜻은 아니다.

### 5.5 저장 실패와 덮어쓰기를 어떻게 처리했는가

- 입력과 출력 경로가 같으면 거부한다.
- 이미 출력 CSV 또는 JSON이 있으면 덮어쓰지 않는다.
- 실제 생성도 `open("x")`로 해 검사와 저장 사이의 충돌을 방어한다.
- 이번 실행이 생성한 경로만 `created_paths`에 기록한다.
- 저장 중 예외가 나면 그 목록을 역순으로 정리하고 원래 예외를 다시 발생시킨다.
- 정리 자체가 실패하면 경고를 남긴다.

`x` 모드는 “새 파일만 생성”이다. 기존 파일을 덮어쓰는 `w` 모드와 다르다.

이것은 일반적인 예외 발생 시 부분 결과를 정리하는 설계다.
운영체제 강제 종료나 전원 차단에도 항상 완전한 두 파일을 보장하는 데이터베이스 트랜잭션은 아니다.

현재 출력이 이미 있으므로 준비 명령을 같은 경로로 다시 실행하면 실패하는 것이 정상이다.
복습은 기존 결과를 읽는 14절 명령으로 진행하면 된다.

## 6. C1: 예측 문제와 열 이름의 계약

### 6.1 목표와 파일

파일: [features.py](/Users/jake/Documents/data-project/src/marine_forecast/features.py)

서로 다른 함수가 “6시간 뒤”, “입력 특성”, “정답 열”을 다른 이름이나 순서로 이해하지 않도록 상수를 정의했다.
이 단계의 산출물은 학습 데이터 자체가 아니라 **공통 계약**이다.

```python
HORIZON_HOURS: int = 6
LAG_HOURS: tuple[int, ...] = (1, 3, 6)

FEATURE_COLUMNS: tuple[str, ...] = (
    "significant_wave_height_m",
    "wind_speed_mps",
    "station_pressure_hpa",
    "wave_height_lag_1h_m",
    "wave_height_lag_3h_m",
    "wave_height_lag_6h_m",
    "wave_height_change_1h_m",
)

TARGET_COLUMN: str = "target_significant_wave_height_6h_m"
```

### 6.2 입력 7개의 의미

| 입력 열                     | 기준시각이 06시일 때 의미 |
| --------------------------- | ------------------------- |
| `significant_wave_height_m` | 06시 유의파고             |
| `wind_speed_mps`            | 06시 풍속                 |
| `station_pressure_hpa`      | 06시 현지기압             |
| `wave_height_lag_1h_m`      | 05시 유의파고             |
| `wave_height_lag_3h_m`      | 03시 유의파고             |
| `wave_height_lag_6h_m`      | 00시 유의파고             |
| `wave_height_change_1h_m`   | 06시 파고 − 05시 파고     |

`lag`는 과거로 얼마나 떨어져 있는지를 뜻한다.
변화량은 상승·하강 추세를 모델에 제공하기 위한 파생 특성이다.
이 특성들이 성능을 반드시 높인다는 사실을 이미 검증한 것은 아니다. 이후 비교 실험 대상이다.

`REQUIRED_OBSERVATION_COLUMNS`는 이 특성을 만들기 위해 원본 관측 표에 필요한 5열이다.
입력 특성 7열과 혼동하지 않는다.

### 6.3 왜 식별자·미래 정답을 입력 열에 포함하지 않았는가

- `station_id`, `observed_at`: 지금은 연결·추적용 정보다. 자동으로 모델 입력이 되는 것은 아니다.
- `target_at`: 언제의 정답인지 추적하는 정보다.
- `TARGET_COLUMN`: 모델이 맞혀야 할 실제 미래 값이므로 입력에 들어가면 안 된다.

특히 정답을 `X`에 넣으면 모델이 미래를 예측하는 대신 답을 보고 맞히게 된다. 이것이 명백한 데이터 누수다.

상수의 튜플은 열 순서도 고정한다. 이후 학습과 API에서 같은 7열을 같은 순서로 선택하게 한다.
다만 대문자 변수 이름과 타입 힌트가 재할당을 언어 차원에서 금지하는 것은 아니다.

## 7. C2: 정제 CSV와 메타데이터 재로딩

### 7.1 목표·입출력

함수: `load_processed_data()`

```python
observations, metadata = load_processed_data(
    "data/processed/buoy_22101_2025_utc_assumed.csv"
)
```

- 입력: 정제 CSV 경로 `str | Path`.
- 내부에서 찾는 파일: 같은 경로의 `.metadata.json`.
- 반환: `(관측 DataFrame, 메타데이터 dict)`라는 튜플.
- 실제 관측 출력: `(8043, 10)`.
- 파일 저장: 없음.

파일이 저장돼 있다는 사실만 믿지 않고, 예상 구조와 맞는지 확인한 뒤 내부 자료형을 복원한다.

### 7.2 정상 실행 순서

1. 경로를 절대경로로 만들고 `.metadata.json` 경로를 계산한다.
2. JSON을 읽어 객체, 즉 Python `dict`인지 검사한다.
3. JSON의 열 목록·출력 UTC·시간대 확인 상태를 확인한다.
4. 지점·시각은 문자열, 수치 8열은 nullable `Float64`로 CSV를 읽는다.
5. 실제 CSV 열 목록·행 수가 기록과 맞는지 검사한다.
6. 지점이 비어 있지 않은지 확인한다.
7. 시각 문자열이 UTC 오프셋 `+00:00` 또는 `Z`로 끝나는지 검사한다.
8. 문자열을 UTC 날짜·시간 타입으로 변환한다.
9. 무한대·중복 키·정렬 상태·열별 결측 수를 검사한다.
10. 시간대 가정 상태를 `attrs`에 붙인다.
11. 미확인 상태라면 경고하고 `(frame, metadata)`를 반환한다.

### 7.3 실제 타입 복원 예

```text
CSV 셀                         메모리의 값·타입
"22101"                    →  "22101", pandas string
"2025-01-01 06:00:00+00:00" →  시간대 포함 Timestamp
"0.5"                      →  0.5, pandas Float64 열
빈 수치 셀                 →  pd.NA
```

현재 날짜 열의 dtype 표시는 `datetime64[us, UTC]`다.
핵심 계약은 `ns`인지 `us`인지보다 **시간대가 포함된 UTC 날짜형**이라는 점이다.

### 7.4 왜 `pd.to_datetime(..., utc=True)`만 쓰지 않았는가

시간대 없는 `"2025-01-01 06:00"`에 `utc=True`를 적용하면 UTC라고 해석할 수 있다.
하지만 C2는 원본 시간대를 새로 추정하는 단계가 아니다.
이미 정제 시 저장한 UTC 표기를 확인하고 읽는 단계다.
그래서 변환 전에 오프셋 존재 여부를 확인한다.

### 7.5 `type(rows) is int`를 사용한 이유

Python에서 `bool`은 `int`의 하위 타입이다.

```python
isinstance(True, int)  # True
type(True) is int      # False
```

행 수 메타데이터가 `true`인데도 정수라고 허용하는 일을 피하려고 정확한 타입을 검사한다.

### 7.6 `attrs`는 무엇인가

```python
observations.attrs["source_timezone"]
# "UTC"

observations.attrs["source_timezone_status"]
# "caller_supplied_unverified"
```

`attrs`는 DataFrame에 붙이는 부가정보 딕셔너리다.
열과 다르므로 `observations.shape`에 포함되지 않고 모델 입력 7열에도 포함되지 않는다.
CSV에 자동 보존되지 않아 JSON과 명시적 복원이 필요하다.

미확인 시간대 경고는 예외와 다르다. 기본 경고 설정에서는 출력 후 계속 실행된다.
경고를 없애려고 확인 상태를 임의로 확정값으로 바꾸면 안 된다.

### 7.7 실패 조건과 검증 한계

- CSV 또는 JSON 없음: `FileNotFoundError`.
- JSON 문법 오류: `JSONDecodeError`.
- 열·행 수·결측 수·정렬 등 불일치: `ValueError`.
- 잘못된 숫자·날짜: 파싱 오류.

C2가 검사하는 것은 구조와 일부 일관성이다.
**모든 수치가 저장 당시와 동일한지 암호학적으로 검증하는 함수는 아니다.**
현재 JSON에는 정제 CSV 자체의 해시가 없으며, 숫자 하나가 다른 유한한 숫자로 바뀌어도
행 수·열·결측 수가 같으면 이 검사만으로는 감지하지 못할 수 있다.
또한 B 단계의 모든 물리 범위 규칙을 C2에서 다시 적용하는 것은 아니다.

C3 이후는 C2와 B의 계약을 통과한 관측을 이어받는 구조다.

## 8. C3: 현재·과거 관측으로 입력 특성 생성

### 8.1 목표·입출력

함수: `build_features(observations)`

```python
features = build_features(observations)
```

- 입력: 내부 형식의 관측 DataFrame. 필요한 원본 열은 5개다.
- 출력: 식별 정보 2열 + 입력 특성 7열의 새 DataFrame.
- 실제 크기 변화: `(8043, 10) → (8043, 9)`.
- 아직 하지 않는 것: 정답 연결, 결측 행 삭제, 모델 학습, 파일 저장.

```text
관측 표
→ 필수 열·키·자료형·중복 검사
→ 현재 관측값 복사
→ 1·3·6시간 전 파고 연결
→ 1시간 변화량 계산
→ 열 순서·행 순서·부가정보 정리
→ 특성 표 반환
```

### 8.2 왜 현재 파고 외에 과거 파고와 변화량을 쓰는가

현재 파고가 똑같이 `0.5m`라도 상황은 다를 수 있다.

```text
상황 A: 0.2 → 0.3 → 0.5m로 상승 중
상황 B: 1.0 → 0.8 → 0.5m로 하강 중
```

현재값만으로는 두 상황을 구별하기 어렵다.
과거값과 변화량을 제공하면 모델이 “현재 상태”와 함께 “최근 변화”의 관계를 학습할 수 있다.
단, 이 정보가 어느 정도 유용한지는 이후 검증 구간의 성능으로 확인해야 한다.

### 8.3 입력 검증은 무엇을 막는가

- 필수 5열 누락, 빈 표.
- 식별 키의 결측, 공백 지점번호.
- 문자열이 아닌 지점 dtype.
- 문자열 시각, 시간대 없는 시각, UTC 이외 시각.
- 같은 관측소·시각의 중복.
- 필요한 관측 수치가 문자열인 경우, 양·음의 무한대.

여기서는 관측 수치의 결측을 허용한다. C3가 결측을 보존해 주어야 C5에서 제외 이유를 설명할 수 있다.

### 8.4 왜 `.shift(1)` 또는 `.shift(6)`를 그대로 쓰지 않는가

`shift()`에 시간 빈도 등 별도 설정 없이 행 수를 전달하면 **행 위치 기준 이동**이다.
한 시간에 한 행이 빠짐없이 존재할 때는 시간 이동처럼 보이지만 누락 시각이 있으면 달라진다.

가상 예시:

| 행 위치 | 관측시각 | 파고 |
| ------: | -------- | ---: |
|       0 | 06:00    |  0.5 |
|       1 | 07:00    |  0.6 |
|       2 | 09:00    |  0.8 |

09시의 이전 행은 07시지만, **1시간 전은 08시**다.
`shift(1)`로 07시 값을 가져오면 2시간 전 관측을 1시간 전이라고 잘못 표시하게 된다.

우리는 `(같은 관측소, 정확한 과거시각)`을 기준으로 연결했다.
이 선택은 실제 파일에 없는 717개 시각 때문에 특히 중요하다.

### 8.5 `pd.Timedelta`는 무엇인가

`Timestamp`는 특정 시점이고 `Timedelta`는 **시간의 길이 또는 두 시점의 차이**다.

```python
point = pd.Timestamp("2025-01-01T08:00:00Z")
duration = pd.Timedelta(hours=1)

point + duration
# Timestamp("2025-01-01 09:00:00+0000", tz="UTC")

pd.Timestamp("2025-01-01T09:00:00Z") - point
# Timedelta("0 days 01:00:00")
```

`pd.Timedelta(hours=hours)`의 `hours`에는 반복문에 따라 실제 정수 `1`, `3`, `6`이 들어간다.
예를 들어 `hours=3`이면 3시간 길이를 생성한다.

날짜형 Series에 더하면 각 행의 시각에 같은 시간 길이가 더해진다.
자정이나 월말을 넘어가도 문자열을 직접 분해할 필요 없이 날짜 계산이 된다.
이 함수는 프로그램을 기다리게 하는 `sleep()`가 아니다.
시간대를 부여하거나 바꾸는 기능도 아니다.

### 8.6 가장 중요한 로직: 과거 특성을 만드는데 왜 시간을 더하는가

핵심 코드:

```python
history = observations.loc[
    :, ["station_id", "observed_at", "significant_wave_height_m"]
].copy()

for hours in LAG_HOURS:
    lag_column = f"wave_height_lag_{hours}h_m"

    shifted = history.rename(
        columns={"significant_wave_height_m": lag_column}
    )

    # 과거값을 참조할 현재 행의 연결 키에 맞춘다.
    shifted["observed_at"] = (
        shifted["observed_at"] + pd.Timedelta(hours=hours)
    )

    result = result.merge(
        shifted,
        on=["station_id", "observed_at"],
        how="left",
        validate="one_to_one",
        sort=False,
    )
```

08시 파고를 09시 행의 “1시간 전 파고”로 넣는 상황을 보자.

**① 원래 관측 표**

| station_id | observed_at | significant_wave_height_m |
| ---------- | ----------- | ------------------------: |
| 22101      | 08:00       |                       0.8 |
| 22101      | 09:00       |                       1.0 |

**② 파고 열 이름을 과거 특성 이름으로 바꾸고, 임시 표의 시각을 +1시간**

| station_id | 연결용 observed_at | wave_height_lag_1h_m |
| ---------- | ------------------ | -------------------: |
| 22101      | 09:00              |                  0.8 |
| 22101      | 10:00              |                  1.0 |

여기서 09시 옆의 `0.8`은 **원래 08시에 관측된 값**이다.
실제 관측을 09시에 발생한 것처럼 고친 것이 아니라, 이 값을 참조할 행의 키를 임시로 만든 것이다.

**③ 현재 표의 같은 관측소·같은 시각에 연결**

| station_id | observed_at | 현재 파고 | 1시간 전 파고 |
| ---------- | ----------- | --------: | ------------: |
| 22101      | 09:00       |       1.0 |           0.8 |

수식으로 쓰면 더 분명하다.

```text
원래 과거 관측시각 = s
그 관측을 h시간 전 값으로 사용할 기준시각 = t

s = t - h
따라서 s + h = t
```

그래서 오른쪽 조회 표의 과거시각에 `h`를 더해 왼쪽 현재시각 `t`와 맞춘다.
같은 방식으로 08시 값에 3시간을 더한 연결 키는 11시다.
이 값은 11시 행의 “3시간 전 파고”가 된다.

각 반복은 원래 `history`에서 새 `shifted`를 만든다.
1시간 더한 표에 다시 3시간을 더해 누적 4시간을 만드는 구조가 아니다.
원본 `observations`의 시각도 바꾸지 않는다.

### 8.7 `merge()`의 각 옵션은 왜 필요한가

- `on=["station_id", "observed_at"]`: 관측소와 시각이 모두 같아야 연결한다.
- `how="left"`: 왼쪽 현재 관측 행은 유지한다. 과거값이 없으면 해당 특성만 결측이 된다.
- `validate="one_to_one"`: 같은 키의 여러 행 때문에 표가 불어나는 잘못된 연결을 거부한다.
- `sort=False`: 결합 단계마다 키 정렬을 요구하지 않는다. 최종 정렬은 함수 끝에서 명시한다.

`left merge` 자체가 언제나 행 수를 보장하는 것은 아니다.
오른쪽 키가 중복이면 한 왼쪽 행이 여러 행으로 늘어날 수 있다.
여기서는 중복 사전 검사와 `one_to_one` 검증을 함께 사용해 현재 행 수를 유지한다.

### 8.8 실제 연간 CSV의 06시 입력 특성을 계산해 보기

아래 값은 가상 예시가 아니라 현재 로컬 연간 파일에서 실행한 실제 결과다.
시각은 현재의 미확인 UTC 가정을 따른다.

| 실제 관측시각, 2025-01-01 | 유의파고(m) |
| ------------------------- | ----------: |
| 00:00                     |         0.5 |
| 03:00                     |         0.6 |
| 05:00                     |         0.6 |
| 06:00                     |         0.5 |
| 12:00                     |         0.6 |

06시의 풍속은 `4.7m/s`, 기압은 `1021.7hPa`다.

따라서 06시 입력 특성은 다음과 같다.

```text
현재 파고:       0.5
현재 풍속:       4.7
현재 기압:    1021.7
1시간 전 파고:   0.6  ← 05시 관측
3시간 전 파고:   0.6  ← 03시 관측
6시간 전 파고:   0.5  ← 00시 관측
1시간 변화량:   -0.1  ← 0.5 - 0.6
```

현재 순서대로 모델 입력을 표현하면:

```python
X_one_row = [0.5, 4.7, 1021.7, 0.6, 0.6, 0.5, -0.1]
```

여기서 `X_one_row`는 설명용 리스트다. 현재 함수가 반환하는 실제 객체는 DataFrame이다.
실수 연산 특성 때문에 내부 계산에서 `-0.099999...`처럼 표시될 수 있다. 의미상 변화량은 약 `-0.1m`다.

### 8.9 실제로 08시 행이 없으면 어떻게 되는가

현재 파일에는 2025-01-01 08시 관측 행이 없다.

09시 결과:

| 항목                |     값 |
| ------------------- | -----: |
| 현재 파고           |    0.5 |
| 1시간 전 파고: 08시 | `<NA>` |
| 3시간 전 파고: 06시 |    0.5 |
| 6시간 전 파고: 03시 |    0.6 |
| 1시간 변화량        | `<NA>` |

07시 파고를 08시 대신 사용하지 않는다.
계산에 필요한 값이 없으므로 변화량도 결측으로 유지한다.
이 행을 버릴지는 C5가 결정한다.

### 8.10 현재·과거 정보와 미래 정보의 경계

C3의 입력은 항상 기준시각 `t` 또는 그 이전 관측이다.
나중 시각의 파고를 바꿨을 때 그보다 앞선 기준시각의 특성이 달라지면 문제가 있다.
C7에서는 이 성질도 테스트했다.

현재는 관측이 관측시각에 이용 가능하다고 가정하는 과거 실험이다.
실제 운영에서는 06시 관측이 06시 10분에 도착할 수 있으므로 수신 지연도 별도로 고려해야 한다.

## 9. C4: 정확히 6시간 뒤 정답 연결

### 9.1 목표·입출력

함수: `attach_targets(features, observations)`

```python
dataset = attach_targets(features, observations)
```

- 입력 1: C3의 특성 표, 실제 `(8043, 9)`.
- 입력 2: C2의 전체 관측 표, 실제 `(8043, 10)`.
- 출력: 정답시각과 실제 미래 파고가 붙은 새 표, `(8043, 11)`.
- 파일 저장·모델 예측: 하지 않는다.

왜 원본 관측 표가 다시 필요한가?
특성 표는 현재와 과거 입력을 정리한 표이고, 미래 정답은 원래 관측 기록에서 조회해야 하기 때문이다.

### 9.2 정상 실행 흐름

```text
특성 표 + 관측 표
→ 두 표의 필수 열·키·시각·중복 확인
→ 정답이 이미 붙었는지 확인
→ 정답 후보 수치·시간대 가정 일치 확인
→ target_at = observed_at + 6시간
→ 원본 관측을 정답 조회 표로 준비
→ (station_id, target_at)로 왼쪽 결합
→ 열 순서·정렬·부가정보 정리
→ dataset 반환
```

### 9.3 `observed_at`과 `target_at`의 차이

- `observed_at`: 예측의 기준이 되는 현재 관측시각 `t`.
- `target_at`: 예측해야 하는 미래 시각 `t + 6시간`.

실제 06시 표본:

```text
observed_at = 2025-01-01 06:00 UTC
target_at   = 2025-01-01 12:00 UTC
```

`target_at`을 6시간 더해 계산하는 것이 예측 자체는 아니다.
단지 **어느 시각의 관측을 정답으로 조회할지 정하는 것**이다.

### 9.4 질문했던 `rename()`은 정확히 무엇을 바꾸는가

핵심 코드:

```python
targets = observations.loc[
    :, ["station_id", "observed_at", "significant_wave_height_m"]
].copy()

targets = targets.rename(
    columns={
        "observed_at": "target_at",
        "significant_wave_height_m": TARGET_COLUMN,
    }
)
```

맞다. `columns={"observed_at": "target_at"}`는 **그 표의 열 이름**을 바꾼다.
시간값 자체에 6시간을 더하는 코드가 아니다.

**변경 전: 원본에서 복사한 조회 표**

| station_id | observed_at | significant_wave_height_m |
| ---------- | ----------- | ------------------------: |
| 22101      | 12:00       |                       0.6 |

**변경 후: 정답 역할이 분명한 이름**

| station_id | target_at | target_significant_wave_height_6h_m |
| ---------- | --------- | ----------------------------------: |
| 22101      | 12:00     |                                 0.6 |

12시 관측이라는 사실은 그대로이고, 학습 데이터에서 이 값이 “미래 정답”으로 쓰인다는 역할만 표시한다.
기본 `rename()`은 새 DataFrame을 반환하므로 `targets = ...`로 그 결과를 받는다.

### 9.5 연결의 왼쪽과 오른쪽을 실제 값으로 보기

왼쪽: 현재 입력과 계산한 정답시각.

```text
station_id=22101, observed_at=06:00, target_at=12:00, 입력 특성 7개
```

오른쪽: 원본 12시 관측에서 이름만 바꾼 정답 조회 표.

```text
station_id=22101, target_at=12:00, 실제 정답=0.6
```

결합:

```python
result = result.merge(
    targets,
    on=["station_id", "target_at"],
    how="left",
    validate="one_to_one",
    sort=False,
)
```

완성한 실제 표본:

```text
식별 정보: 관측소 22101, 기준시각 06:00, 정답시각 12:00
입력 X:   [0.5, 4.7, 1021.7, 0.6, 0.6, 0.5, -0.1]
정답 y:   0.6m
```

이 한 행이 의미하는 것은 “이런 현재·과거 상태를 보였던 날, 실제 6시간 뒤 파고는 0.6m였다”다.

### 9.6 C3에서는 시간을 옮기고 C4에서는 열 이름을 바꾸는 차이

| 단계         | 왼쪽에 맞출 시각             | 오른쪽 조회 표 처리                                           |
| ------------ | ---------------------------- | ------------------------------------------------------------- |
| C3 과거 입력 | 현재 `t`                     | 과거시각 `s`에 `h`를 더해 `s+h=t`로 맞춤                      |
| C4 미래 정답 | 미리 계산한 `target_at=t+6h` | 미래 관측시각 값은 그대로 두고 열 이름을 `target_at`으로 바꿈 |

둘 다 **의도한 시각의 값만 정확히 연결하는 작업**이다.
관측값을 예측값으로 변환하는 알고리즘은 아니다.

### 9.7 미래 관측이 없으면 왜 즉시 행을 버리지 않는가

정확한 미래시각의 행이 없거나 그 행의 파고가 비어 있으면 정답은 결측이다.
현재 데이터에서 정답이 없는 행은 총 **674개**다.

데이터 끝부분뿐 아니라 연중 중간에도 미래 관측이 빠져 있을 수 있다.
근처 시각의 관측으로 대신 채우지 않는다.
현재 버전의 문제는 “정확히 6시간 뒤”이기 때문이다.

C4는 연결에 집중하고 C5가 제외 결정을 맡는다.
이렇게 해야 `정답만 없음`, `입력만 없음`, `둘 다 없음`을 구분해 설명할 수 있다.

### 9.8 실패 조건과 부가정보

- 두 입력 중 필요한 열·행·키가 없거나 시각 형식이 잘못된 경우.
- 같은 관측소·시각의 중복.
- 특성 표에 이미 `target_at` 또는 정답 열이 있음.
- 원본 정답 파고가 숫자형이 아니거나 무한대임.
- 두 표의 `source_timezone` 또는 `source_timezone_status`가 다름.

성공하면 입력 특성 표의 `attrs`를 이어받고 `horizon_hours=6`을 추가한다.
단, 같은 가정을 썼다는 검사는 **그 가정이 사실이라는 확인**과 다르다.

### 9.9 미래 정답을 붙이는 것은 왜 데이터 누수가 아닌가

지도학습 데이터에는 미래 실제값을 정답 `y`로 붙여야 한다.
누수는 이 미래값이 입력 `X`로 들어가거나, 학습·모델 선택 과정에 잘못 섞일 때 발생한다.

따라서 현재 설계는 다음 둘을 분리한다.

```text
X: t 시각까지의 정보만 사용
y: t+6시간의 실제값, 정답 역할로만 사용
```

정답이 한 DataFrame 안에 있다는 사실보다 **모델에 전달할 열을 정확히 제한하는 것**이 중요하다.
이후에는 반드시 `FEATURE_COLUMNS`와 `TARGET_COLUMN`으로 따로 선택해야 한다.

## 10. C5: 완전한 표본 선택과 제외 내역 집계

### 10.1 목표·입출력

함수: `select_complete_samples(dataset)`

```python
complete_samples, selection_report = select_complete_samples(dataset)
```

- 입력: C4의 정답 연결 표 `(8043, 11)`.
- 반환 1: 입력 7개와 정답이 모두 있는 표 `(5756, 11)`.
- 반환 2: 제외 이유를 집계한 `dict[str, object]`.
- 아직 하지 않는 것: 결측 보간·평균 대체·모델 학습·시간 분할.

```text
정답이 붙은 표
→ 필수 열·키·숫자형·무한대 검사
→ 입력 결측 마스크 생성
→ 정답 결측 마스크 생성
→ 둘 중 하나라도 결측이면 제외
→ 완전한 행 선택·인덱스 정리
→ 선택 결과와 제외 보고서 반환
```

### 10.2 주요 로직을 한 줄씩 이해하기

```python
# 각 행에서 입력 특성 7개 중 하나라도 비었는지 확인한다.
missing_features = dataset[list(FEATURE_COLUMNS)].isna().any(axis=1)

# 정답이 없는 행을 별도로 표시한다.
missing_target = dataset[TARGET_COLUMN].isna()

# 입력 또는 정답 중 하나라도 없으면 제외 대상으로 표시한다.
excluded = missing_features | missing_target

# 제외 대상이 아닌 행만 복사하고 0부터 새 인덱스를 부여한다.
complete_samples = dataset.loc[~excluded].copy().reset_index(drop=True)
```

`dataset[입력 7열].isna()`는 행·열별로 True/False를 가진 DataFrame이다.
`.any(axis=1)`은 각 행을 가로질러 검사해 **행별 Boolean Series**로 줄인다.
`missing_target`도 원래 행 인덱스와 대응하는 Boolean Series다.

### 10.3 5행의 가상 예시로 마스크를 따라가기

| 행  | 입력 중 결측        | 정답 결측 | `missing_features` | `missing_target` | `excluded` | 처리        |
| --- | ------------------- | --------- | ------------------ | ---------------- | ---------- | ----------- |
| A   | 없음                | 없음      | False              | False            | False      | 유지        |
| B   | 1시간 전 파고 없음  | 없음      | True               | False            | True       | 입력만 결측 |
| C   | 없음                | 있음      | False              | True             | True       | 정답만 결측 |
| D   | 3시간 전 파고 없음  | 있음      | True               | True             | True       | 둘 다 결측  |
| E   | 없음, 현재 파고는 0 | 없음      | False              | False            | False      | 유지        |

```text
excluded  = [False, True, True, True, False]
~excluded = [True, False, False, False, True]

dataset.loc[~excluded] → A, E 행 유지
```

`~`는 Boolean Series의 각 True/False를 뒤집는다.
Python의 단일 값 연산인 `not`을 Series 전체에 대신 쓰면 안 된다.

### 10.4 제외 이유를 서로 겹치지 않게 세는 방법

```python
missing_features_only = missing_features & ~missing_target
missing_target_only = ~missing_features & missing_target
missing_both = missing_features & missing_target
```

- `|`: 각 행에서 OR, 둘 중 하나라도 True.
- `&`: 각 행에서 AND, 둘 다 True.
- `~`: 각 행의 Boolean 반전.

입력 결측 수와 정답 결측 수를 그냥 더하면 D 같은 행을 두 번 센다.
그래서 세 그룹으로 나눠 합이 전체 제외 수와 맞도록 했다.

### 10.5 실제 보고서

```python
{
    "total_rows": 8043,
    "usable_rows": 5756,
    "excluded_rows": 2287,
    "missing_features_only": 1613,
    "missing_target_only": 485,
    "missing_both": 189,
    "missing_per_feature": {
        "significant_wave_height_m": 24,
        "wind_speed_mps": 0,
        "station_pressure_hpa": 0,
        "wave_height_lag_1h_m": 658,
        "wave_height_lag_3h_m": 676,
        "wave_height_lag_6h_m": 672,
        "wave_height_change_1h_m": 669,
    },
}
```

확인할 관계:

```text
1,613 + 485 + 189 = 2,287행 제외
8,043 - 2,287 = 5,756행 유지

입력에 결측이 있는 행 = 1,613 + 189 = 1,802
정답이 없는 행       =   485 + 189 =   674
```

`missing_per_feature`의 합은 결측 **셀 수**를 더한 것이므로 결측 **행 수**와 같지 않을 수 있다.
한 행의 1시간 전 파고와 변화량이 함께 비면 두 열에서 각각 집계된다.

### 10.6 실제 09시 행이 제외되는 이유

C3에서 봤던 2025-01-01 09시 행은:

```text
현재값: 존재
1시간 전 파고: 없음
변화량: 없음
15시 실제 정답: 0.7m, 존재
```

따라서 `missing_features=True`, `missing_target=False`다.
`missing_features_only`에 집계되며 학습 표본에서는 제외된다.

### 10.7 왜 그냥 `dataset.dropna()`라고 하지 않았는가

현재 11열 표만 보면 비슷한 결과가 나올 수 있지만, 의도를 명시하는 것이 중요하다.

- 모델이 쓰는 입력과 정답을 기준으로 결측을 판단한다.
- 나중에 사용하지 않는 참고 열을 추가해도 그 열이 비었다고 표본을 버리지 않는다.
- 어떤 이유로 몇 행이 사라졌는지 보고서를 만들 수 있다.
- 숫자형이 아닌 값이나 무한대를 단순 결측처럼 취급해 조용히 버리지 않는다.

C7에서는 사용하지 않는 추가 열이 전부 결측이어도 표본을 유지하는 상황을 테스트했다.

### 10.8 왜 초기 버전에서는 결측을 채우지 않는가

간단하고 설명 가능한 출발점을 만들기 위해 완전한 표본만 사용한다.
무작정 평균으로 채우거나 미래값을 이용해 보간하면 데이터 의미가 달라지거나 누수가 생길 수 있다.

다만 완전한 표본만 선택하는 방식에도 단점이 있다.
전체 8,043행 중 2,287행이 제외되고, 제외된 시각이 특정 계절·기상 상태에 몰리면 표본 편향이 생길 수 있다.
현재는 제외 수를 기록했고, 제외 분포와 기상 조건별 편향은 추가 분석 과제다.

모든 행이 제외되어도 C5는 빈 표와 보고서를 반환할 수 있다.
그 뒤 C6가 빈 표 입력을 거부한다. 빈 결과를 확인 없이 학습에 넘기면 안 된다.

## 11. C6: 시간순 분할과 경계 정답 제외

### 11.1 목표·입출력

함수: `split_by_time()`

```python
splits, split_report = split_by_time(
    complete_samples,
    validation_start="2025-10-01T00:00:00Z",
    test_start="2025-12-01T00:00:00Z",
    test_end="2026-01-01T00:00:00Z",
)
```

- 입력: 결측 표본 선택이 끝난 5,756행과 시간대가 명시된 경계 3개.
- 반환 1: `train`, `validation`, `test` DataFrame을 가진 딕셔너리.
- 반환 2: 사용·제외·경계 필터 수를 기록한 딕셔너리.
- 모델 학습·성능 평가는 하지 않는다.

```python
train = splits["train"]
validation = splits["validation"]
test = splits["test"]
```

### 11.2 세 구간은 각각 어떤 역할인가

| 구간   | 이후 사용할 목적             | 하지 말아야 할 일                         |
| ------ | ---------------------------- | ----------------------------------------- |
| 학습   | 모델의 계수·규칙 학습        | 검증·테스트 정답을 섞어 학습하기          |
| 검증   | 모델·특성·설정 비교와 선택   | 검증 점수를 최종 독립 성능이라고 과장하기 |
| 테스트 | 선택이 끝난 모델의 최종 평가 | 결과를 반복해 보며 모델을 계속 선택하기   |

테스트 구간의 **행 수·연결 무결성**을 확인하는 것과, 테스트 **예측 오차를 보고 모델을 조정**하는 것은 다르다.
우리는 아직 예측 오차를 계산하지 않았다.

### 11.3 현재 구간을 정확히 이해하기

현재 내부 UTC 기준 구간:

```text
학습: observed_at < 2025-10-01 00:00
      → 현재 데이터에서는 1~9월

검증: 2025-10-01 00:00 <= observed_at < 2025-12-01 00:00
      → 10~11월

테스트: 2025-12-01 00:00 <= observed_at < 2026-01-01 00:00
        → 12월
```

“1~10월 학습, 11~12월 검증, 12월 테스트”가 아니다.
경계가 10월 1일이므로 **10월은 검증 구간**이다.
각 구간의 시작은 포함하고 끝은 제외하는 `[시작, 끝)` 형태다.

단, 이것은 먼저 기준시각으로 나눈 후보 구간이고, 아래 정답시각 조건도 통과해야 최종 표본이 된다.

### 11.4 랜덤 분할 대신 시간순으로 나눈 이유

목표는 과거로 미래를 예측하는 것이다.
랜덤 분할은 이후 시점의 패턴을 학습에 넣고 이전 시점을 평가하는 상황을 만들 수 있다.
시간적으로 가까운 관측이 강하게 연관되어 있으면 성능도 실제 운영보다 낙관적으로 보일 수 있다.

그래서 먼저 과거 학습 → 이후 검증 → 더 이후 테스트 순서를 고정했다.
다만 1년의 고정 분할 하나만으로 모든 계절·연도에 대한 일반화가 검증되는 것은 아니다.
지금 분할은 검증과 테스트가 특정 계절에 치우쳐 있다는 한계도 있다.

### 11.5 기준시각만 나누면 생기는 문제

학습 종료 경계를 10월 1일 00시로 정했다고 하자.

가상 표본:

```text
observed_at = 9월 30일 20시
target_at   = 10월 1일 02시
```

기준시각은 학습 구간이지만 정답은 검증 구간이다.
이 행을 학습에 넣으면 “검증 시작 전까지 확보한 정답으로 학습했다”는 조건을 위반한다.
따라서 정답시각도 해당 구간 끝보다 **엄격히 이전**이어야 한다.

핵심 코드:

```python
usable_mask = window_mask & (target_at < period_end)
```

`window_mask`는 기준시각이 해당 구간에 속하는지 나타낸다.
`target_at < period_end`는 그 표본의 실제 정답도 구간 안에 있는지 나타낸다.
두 조건을 모두 만족하는 표본만 유지한다.

### 11.6 왜 `<`이고 `<=`가 아닌가

학습 경계가 `2025-10-01 00:00`일 때 설명용 예시:

| 기준시각    | 정답시각, +6시간 | 학습 사용 여부    |
| ----------- | ---------------- | ----------------- |
| 09-30 17:00 | 09-30 23:00      | 사용              |
| 09-30 18:00 | 10-01 00:00      | 제외: 경계와 같음 |
| 09-30 20:00 | 10-01 02:00      | 제외: 경계를 넘음 |

10월 1일 00시는 이미 검증 구간의 시작이다.
따라서 학습 정답에 포함하지 않기 위해 `<`를 쓴다.

이런 처리를 여기서는 경계 정답 제외 또는 경계 퍼지라고 부른다.
행 개수로 “마지막 6행 삭제”하는 방법이 아니라 실제 시각으로 판단한다.

### 11.7 검증 첫날 입력이 학습 기간의 과거 관측을 참조해도 되는가

예를 들어 검증 기준시각이 10월 1일 02시라면 6시간 전 파고는 9월 30일 20시다.
이 과거값을 입력에 쓰는 것은 현재의 연속 운영 가정에서는 가능하다.
10월 1일 02시에 실제 예측을 한다면 그보다 이전의 관측을 볼 수 있기 때문이다.

구분해야 하는 것은 다음이다.

```text
검증 시각의 입력에 과거 관측을 사용 → 가능, 예측 시점에 이미 알 수 있는 정보
학습 표본의 정답이 검증 시작 이후임 → 현재 설계에서는 제외
검증 시각 이후의 관측을 검증 입력에 사용 → 안 됨
```

그래서 특성은 전체 관측에서 **과거 방향으로만** 만들고, 완전한 표본을 시간순으로 분리해도 된다.
하지만 전체 데이터의 평균·표준편차를 먼저 계산해 정규화하는 것까지 허용되는 것은 아니다.
향후 스케일러·결측 대체기처럼 데이터에서 설정을 학습하는 전처리는 학습 구간에서만 `fit()`해야 한다.

### 11.8 정상 실행 순서

1. 전체 필수 열·비어 있지 않은 입력을 확인한다.
2. 필요한 값이 결측이면 C5를 먼저 수행하라고 오류를 낸다.
3. 기준시각·정답시각이 UTC 날짜형인지 확인한다.
4. 중복 키를 검사한다.
5. 모든 `target_at - observed_at`이 정확히 6시간인지 검사한다.
6. 경계 문자열을 `pd.Timestamp`로 바꾸고 시간대 포함 여부를 검사한다.
7. 경계를 UTC로 바꾸고 `validation_start < test_start < test_end`인지 확인한다.
8. 원본을 변경하지 않고 결과용 표를 기준시각·관측소 순으로 정렬한다.
9. 각 구간의 기준시각 마스크와 정답시각 조건으로 선택한다.
10. 빈 구간이 있으면 실패한다.
11. `attrs`에 구간 이름·끝 경계를 기록하고 표들과 보고서를 반환한다.

이 함수는 C5 이후 입력을 전제로 한다.

실제 데이터만 사용하면 결과가 어긋났을 때 코드가 잘못됐는지 입력이 잘못됐는지 구분하기 어렵다.
그래서 작은 독립 예제로 로직을 검증하고 실제 파일로 연결도 확인한다.

가상 값이 실제 기상 범위를 대표하는 것은 아니다.
이 테스트는 주로 시각·관측소 연결과 선택 로직을 분리해 검증하기 위한 것이다.

### 12.4 `fixture`, `parametrize`, `raises`, `warns`

```python
@pytest.fixture
def observations() -> pd.DataFrame:
    # 여러 테스트에 사용할 작은 관측 표를 만든다.
    ...
```

fixture는 테스트 준비 데이터를 제공한다.
기본 함수 범위 fixture는 테스트 호출마다 새로 실행되므로 한 테스트의 수정이 다른 테스트에 번지지 않도록 돕는다.

```python
@pytest.mark.parametrize("hours", [1, 3, 6])
def test_exact_lag(observations, hours):
    ...
```

위 예시는 하나의 함수 정의를 `hours=1`, `3`, `6`으로 각각 실행해 **3개의 테스트 케이스**로 수집한다.
따라서 함수 정의 수와 pytest가 수집한 테스트 수는 다를 수 있다.

```python
with pytest.raises(ValueError, match="Duplicate"):
    build_features(duplicated_observations)
```

기대한 예외가 발생해야 성공하는 테스트다.
예외를 내야 하는데 조용히 통과하면 테스트가 실패한다.

```python
with pytest.warns(UserWarning, match="Source timezone is not confirmed"):
    observations, metadata = load_processed_data(path)
```

확인되지 않은 가정을 숨기지 않고 경고하는지 검사한다.
경고는 기대된 동작이며 모델 성능 실패를 뜻하지 않는다.

### 12.5 왜 `assert_frame_equal()`을 쓰는가

## 13. 헷갈렸던 pandas·Python 문법과 오류 복습

### 13.1 DataFrame, Series, list, dict는 어떻게 다른가

```text
DataFrame: 행과 열이 있는 2차원 표
Series:    인덱스 라벨과 dtype을 가진 1차원 데이터
list:      위치 기반의 Python 순서 자료구조
dict:      키와 값을 대응시키는 Python 매핑
```

Series는 리스트와 비슷하게 여러 값을 담지만 리스트 자체가 아니다.
라벨로 값을 조회할 수 있어 딕셔너리와 닮았지만 딕셔너리 자체도 아니다.
Series의 인덱스는 중복될 수 있고, 연산 시 라벨을 맞추는 특징이 있다.

```python
s = pd.Series([0.5, 0.7], index=["06시", "07시"], dtype="Float64")

s.loc["06시"]  # 라벨 기반: 0.5
s.iloc[0]      # 위치 기반: 0.5
s.tolist()     # Python 리스트로 변환: [0.5, 0.7]
```

현재 코드의 `observations["significant_wave_height_m"]`은 Series다.
`observations[["station_id", "observed_at"]]`은 두 열을 가진 DataFrame이다.

### 13.2 mask는 별도의 특별한 클래스 이름이 아니다

여기서 mask는 “선택하거나 제외할 위치를 표시하는 True/False 데이터”를 뜻한다.

```python
mask = pd.Series([False, True, False, True], index=[0, 1, 2, 3])
```

`invalid_mask`, `excluded`, `usable_mask`는 용도별 변수 이름이며 보통 Boolean Series다.

### 13.3 질문했던 `invalid_mask[invalid_mask]`

```python
invalid_mask = pd.Series([False, True, False, True], index=[0, 1, 2, 3])

invalid_mask[invalid_mask]
# 1    True
# 3    True

invalid_mask[invalid_mask].index[0]
# 1
```

- 바깥 `invalid_mask[...]`: 선택 대상 Series.
- 대괄호 안 `invalid_mask`: True 위치만 남기라는 선택 조건.
- `.index`: 남은 행 라벨 `[1, 3]`.
- `.index[0]`: 그중 첫 라벨 `1`.

따라서 “마스크 값이 1인 원소를 찾는다”가 아니라 **True 위치를 필터링한 뒤 첫 행 라벨을 얻는 것**이다.
원본 셀은 `raw.at[index, column]`으로 읽는다.

### 13.4 `.any()`와 `.sum()`

```python
mask = pd.Series([False, True, True])

mask.any()  # True: 적어도 하나가 참인가?
mask.sum()  # 2: 참이 몇 개인가?
```

`True`를 1, `False`를 0처럼 집계하므로 결측 개수를 셀 수 있다.

```python
df.isna().sum()        # 열별 결측 셀 수
df.isna().any(axis=1)  # 행별로 결측이 하나라도 있는지
df.isna().any().any()  # 표 전체에 결측이 하나라도 있는지
```

### 13.5 `df.shape`이지 `pd.shape`가 아니다

`pd`는 pandas 라이브러리 별칭이고, `df`는 실제 표 객체다.

```python
print(df.shape)   # 예: (8043, 10)
print(df.dtypes)  # 열별 자료형
print(df.columns.tolist())
print(df.isna().sum())
```

`shape`는 속성이므로 `df.shape()`처럼 호출하지 않는다.
반대로 `head()`, `sum()`, `isna()`는 메서드여서 괄호가 필요하다.

Python 대화형 셸에서는 단독 표현식 결과를 표시할 수 있지만,
`.py` 파일이나 `python -c` 실행에서는 `df.shape`만 적으면 값이 자동 출력되지 않는다.
확실히 확인하려면 `print(df.shape)`를 사용한다.
`>>>`, `...`는 셸 프롬프트 표기이므로 코드 파일에 복사하지 않는다.

### 13.6 `.loc`, `.iloc`, `.copy()`, `reset_index(drop=True)`

```python
selected = dataset.loc[~excluded, list(FEATURE_COLUMNS)].copy()
```

- `.loc[행 조건, 열 선택]`: 라벨·조건 기반 선택.
- `.iloc[0]`: 첫 번째 위치의 행.
- `.copy()`: 원본과 구분되는 결과 객체를 명시적으로 만든다.
- `.reset_index(drop=True)`: 이전 인덱스를 열로 남기지 않고 0부터 다시 부여한다.

행을 골라 `[0, 3, 9]`만 남기면 인덱스 라벨도 그렇게 남을 수 있다.
재설정하면 `[0, 1, 2]`가 된다.
관측 식별자는 인덱스 번호가 아니라 `station_id`와 `observed_at`이다.

### 13.7 `.rename()`과 값 계산은 다르다

```python
renamed = frame.rename(columns={"observed_at": "target_at"})
```

위 코드는 열 이름 변경이다. 시간값에 6시간을 더하는 것은 다음 코드다.

```python
result["target_at"] = result["observed_at"] + pd.Timedelta(hours=6)
```

열 이름 변경과 실제 값 변환을 구분해서 읽어야 한다.

### 13.8 `tuple` 반환과 언패킹

```python
complete_samples, report = select_complete_samples(dataset)
```

함수는 두 값을 담은 튜플 `(complete_samples, report)`를 반환한다.
왼쪽의 두 변수로 각각 받는 것을 언패킹이라고 한다.
DataFrame 안에 보고서 열이 추가되는 것은 아니다.

`tuple[int, ...]`는 정수 여러 개를 담는 튜플 타입 힌트다.
`dict[str, object]`는 문자열 키에 다양한 타입의 값을 담는 딕셔너리라는 설명이다.
타입 힌트만으로 실행 시 입력을 자동 검증하지는 않는다.

### 13.9 `*` 뒤의 인자는 이름으로 전달한다

```python
def split_by_time(samples, *, validation_start, test_start, test_end):
    ...
```

`*` 뒤의 인자는 키워드 인자다.
세 개의 날짜 문자열을 순서만으로 넘겨 뒤바꾸는 실수를 줄이려고 이름을 명시하도록 했다.

### 13.10 `.attrs.copy()`의 의미와 한계

```python
result.attrs = observations.attrs.copy()
```

부가정보 딕셔너리를 얕게 복사한다.
지금 시간대 상태처럼 문자열 값 위주인 메타데이터를 전달하는 데 적합하다.
내부에 중첩 리스트나 딕셔너리가 추가된다면 얕은 복사가 그 내부 객체까지 독립적으로 복사하는 것은 아니라는 점에 주의한다.

### 13.11 `Path.parents[1]` 복습

현재 테스트 파일 기준:

```python
file = Path("/Users/jake/Documents/data-project/tests/test_dataset.py")

file.parents[0]  # /Users/jake/Documents/data-project/tests
file.parents[1]  # /Users/jake/Documents/data-project
```

### 13.12 `uv run --locked` 복습

`uv`는 Python 환경·패키지 의존성을 관리하는 도구다.

```bash

```

`--locked`는 현재 설정 때문에 잠금 파일을 갱신해야 하는 상황이면 변경하지 않고 실패하도록 한다.
“네트워크를 절대 사용하지 않는다”거나 “환경에 어떤 변경도 하지 않는다”는 뜻은 아니다.
현재 환경의 Python을 직접 쓰려면 이 문서처럼 `.venv/bin/python`으로 실행할 수도 있다.

### 13.13 실제 발생했던 `observation_at` 오타 오류

당시 traceback 마지막 부분:

```text
ValueError: features: missing columns: ['observation_at']
```

실제 프로젝트 계약의 열 이름은 `observed_at`인데, 필요한 열 검사에서 `observation_at`을 요구했다.
숫자나 파일 인코딩 문제가 아니라 **열 이름의 철자 불일치**였다.

이 오류를 읽는 순서:

1. 마지막 예외에서 빠진 이름 `observation_at` 확인.
2. 최초로 예외를 발생시킨 `attach_targets()`의 필수 열 검사 위치 확인.
3. `features.columns.tolist()`로 실제 열 이름 확인.
4. 실제 `observed_at`과 기대 `observation_at` 비교.
5. 계약에 맞춰 잘못된 열 이름을 수정.
6. 정답 연결 테스트와 전체 테스트 재실행.

현재 코드의 해당 키는 `observed_at`으로 통일되어 있다.
C7의 전체 연결 테스트도 정상 표를 잘못 거부하는 이런 회귀를 잡는 데 도움이 된다.

### 13.14 주석 언어와 인코딩 문제를 혼동하지 않기

이전에 설명 코드에 일본어 주석·docstring이 섞인 것은 CSV 인코딩 문제와 별개였다.
데이터가 깨져 일본어가 생긴 것이 아니라, 설명에 사용한 자연어가 잘못된 것이다.
앞으로 추가하는 설명과 테스트 주석은 한글 기준으로 읽으면 된다.
기존 소스에 남아 있는 일부 영어 주석은 데이터 처리 결과를 바꾸지 않는다.

### 15.2 다음에는 먼저 지속성 기준 모델을 만든다

예측값을 현재 파고와 같다고 두는 간단한 기준이다.

```text
현재 06시 파고가 0.5m
→ 12시 예측도 0.5m로 둠
실제 12시 파고가 0.6m
→ 이 표본의 오차는 예측 - 실제 = -0.1m
→ 절대오차는 0.1m
```

복잡한 모델을 만들기 전에 “현재값을 그대로 쓰는 것보다 나은가?”라는 비교 기준이 필요하다.
이 모델은 계수를 학습하는 일반 회귀 모델과 달리 현재 파고를 복사하는 규칙이다.

뒤이어 간단한 회귀 모델과 트리 계열 모델 등을 같은 표본·같은 지표로 비교할 수 있다.
이것은 다음 작업 방향 설명이며, 이 문서를 작성하며 모델 코드를 추가한 것은 아니다.

### 15.3 MAE·RMSE는 무엇을 볼 것인가

아래는 실제 성능 결과가 아니라 지표 이해를 위한 가상 예시다.

```text
실제값: [0.6, 1.0]
예측값: [0.5, 1.3]
오차:   [-0.1, 0.3]

MAE  = (0.1 + 0.3) / 2 = 0.2m
RMSE = sqrt((0.1² + 0.3²) / 2) ≈ 0.224m
```

MAE는 평균적인 절대오차를 해석하기 좋고, RMSE는 큰 오차에 더 큰 영향을 받는다.
전체 수치뿐 아니라 높은 파고를 실제보다 낮게 예측하는 경우도 살펴봐야 한다.
높은 파고 구간의 기준과 최종 평가 방식은 테스트 성능을 보기 전에 정한다.

### 15.4 API까지 연결할 때 재사용되는 부분

학습 시:

```text
과거 관측 → build_features() → attach_targets() → 표본 선택·시간 분할 → 학습·평가
```

추론 시 계획:

```text
최근 관측 → 같은 build_features() → 예측 시점의 입력 7열 → 저장한 모델 → 예측값
```

실시간 API는 미래 정답이 없으므로 `attach_targets()`나 C5를 그대로 호출하는 구조가 아니다.
최신 입력 7개가 모두 준비됐는지 별도로 확인해야 한다.
“6시간의 이력”도 정확히 필요한 과거시각을 포함해야 하며, 누락 관측이면 입력 부족으로 처리해야 한다.

한 표본을 추론하려고 전체 연간 데이터를 매 요청마다 읽을 필요도 없다.
모델 저장·최근 이력 관리·추론용 검증은 이후 단계의 책임이다.

별도 GPU 서버나 대형 언어 모델이 지금의 회귀 문제에 필수인 것은 아니다.
우선은 데이터에서 예측까지 이어지는 작고 설명 가능한 시스템을 완성하는 것이 목표다.

### 15.5 계속 기억해야 할 한계

- 한 관측소·한 해 자료의 결과를 모든 해역·모든 연도로 일반화하지 않는다.
- 파일의 결측과 없는 시각의 원인은 아직 확정하지 않았다.
- 완전한 표본 선택으로 자료가 많이 줄고, 선택 편향이 생길 수 있다.
- 시간대 미확인은 실제 시각·달력 구간 해석에 영향을 준다.
- 관측값이 즉시 이용 가능하다고 가정했고, 실제 수신 지연을 검증하지 않았다.
- 기본 수치 검사 통과가 센서 품질 보증을 의미하지 않는다.
- 테스트 통과가 모델 성능이나 운영 안정성의 증거는 아니다.
- 현재는 해양기상 수치 예측 프로젝트이며 실제 해군 임무 수행 가능성이나 사고 확률을 검증한 시스템이 아니다.

## 17. 면접 심화: 가장 어려웠던 문제 — 불규칙한 관측 간격과 시간 기준 연결

### 17.1 이 경험을 어떤 이름으로 설명하면 좋은가

우리가 해결한 문제는 **“불규칙한 관측 간격에서도 정확한 시간 차이를 기준으로 학습 표본을 구성하는 문제”**다.

“유동적인 시간 설정”이라고만 말하면 예측 간격을 요청마다 자유롭게 바꿨거나,
원본 관측시각을 임의로 바꿨다는 의미로 들릴 수 있다.
현재 예측 간격은 6시간이고, 과거 입력 간격은 1·3·6시간으로 고정되어 있다.
유동적인 것은 파일에 실제로 존재하는 관측시각의 간격이지, 정답의 정의가 아니다.

따라서 면접에서는 다음과 같이 표현하면 정확하다.

> 가장 어려웠던 점은 시간자료라고 해서 모든 시각의 관측이 연속적으로 존재하는 것은 아니라는 점이었습니다.
> 그래서 행 순서가 아니라 관측소와 실제 시각을 기준으로 과거 입력과 미래 정답을 연결했습니다.

### 17.2 처음에 무엇을 예상했고, 실제로 무엇이 달랐는가

시간 단위 자료를 다운로드했으므로 처음에는 다음과 같이 생각하기 쉽다.

```text
1행 뒤 = 1시간 뒤
6행 뒤 = 6시간 뒤
```

그러나 실제 파일에는 일부 시각의 행이 없었다.
어떤 날은 08시 관측이 없고, 다른 날은 다른 시각의 관측이 없는 식으로
날짜마다 존재하는 시각이 달라질 수 있었다.

여기서 두 문제를 구분해야 한다.

- **정렬 문제**: 12시, 06시, 10시 순서로 행이 섞여 있다면 정렬로 해결할 수 있다.
- **누락 시각 문제**: 정렬 후에도 07시 다음이 09시라면 08시 행은 여전히 없다. 정렬만으로 해결되지 않는다.

현재 실제 연간 자료에서 중요한 문제는 두 번째였다.
파일에 없는 시각의 원인이 장비 고장인지, 다운로드 범위·필터인지, 제공 방식인지까지는 확인하지 않았다.
따라서 “센서 고장으로 불규칙해졌다”라고 단정하지 않는다.

### 17.3 실제 파일의 예: 6행 뒤가 6시간 뒤가 아니었다

현재 연간 CSV의 2025-01-01에는 다음 순서로 관측이 존재한다.
아래 시각은 기존 실험의 미확인 UTC 가정을 유지한 표현이다.

| 06시 행에서 떨어진 행 수 | 실제 관측시각 | 06시와의 시간 차이 |
| -----------------------: | ------------- | ------------------ |
|                        0 | 06:00         | 0시간              |
|                        1 | 07:00         | 1시간              |
|                        2 | 09:00         | 3시간              |
|                        3 | 10:00         | 4시간              |
|                        4 | 11:00         | 5시간              |
|                        5 | 12:00         | 6시간              |
|                        6 | 13:00         | 7시간              |

08시 행이 없기 때문에 06시 기준 **6시간 뒤인 12시는 5행 뒤**이고,
**6행 뒤인 13시는 7시간 뒤**다.

미래 정답을 단순히 `shift(-6)`으로 붙이면 이 표본은 12시가 아니라 13시 관측을 정답으로 삼게 된다.
값이 우연히 같더라도 시각상 잘못 연결된 표본이다.

과거 입력도 마찬가지다. 09시의 바로 이전 행은 07시지만,
09시의 1시간 전은 08시이므로 07시 관측을 1시간 전 특성으로 사용하면 안 된다.

### 17.4 왜 이것이 모델을 바꾸는 것보다 먼저 해결해야 할 문제였는가

행 이동으로 정답을 붙이면 어떤 표본은 6시간 뒤, 다른 표본은 7시간 또는 그 이후를 맞히는 문제가 된다.
그런 표본들을 모두 “6시간 뒤 예측”이라고 학습·평가하면 목표가 일관되지 않다.

```text
명시한 문제: X(t)로 y(t+6시간)를 예측

잘못된 구현:
  표본 A는 y(t+6시간)
  표본 B는 y(t+7시간)
  표본 C는 더 먼 시각의 실제값
```

이는 단순히 예측 오차가 커지는 문제를 넘어,
성능 지표가 애초에 의도한 6시간 예측 능력을 측정하지 못하게 만든다.
따라서 복잡한 모델을 적용하기 전에 학습 문제의 시간 기준을 바로잡는 것이 우선이었다.

### 17.5 해결 로직: 행 번호를 버리고 관측소·시각을 연결 키로 사용

전체 해결 과정:

```text
시간 문자열을 날짜형으로 변환하고 내부 시간 기준 통일
→ (관측소, 관측시각) 중복 검사·정렬
→ 정확히 t-1시간, t-3시간, t-6시간 관측을 조회해 입력 생성
→ 정확히 t+6시간 관측을 조회해 정답 생성
→ 해당 시각이 없으면 결측으로 보존
→ 입력·정답이 완전한 표본만 선택하고 제외 내역 기록
→ 시간 분할 후 정답시각도 구간 경계를 넘지 않는지 확인
```

**① 과거 입력: `build_features()`**

원하는 입력은 같은 관측소의 `t-h` 시각 파고다.
조회용 표의 과거시각 `s`에 `h`를 더해 `s+h=t`가 되도록 만든 뒤 현재 행과 결합했다.

```python
# 원본 관측이 아니라 복사한 조회용 표의 연결 시각만 이동한다.
shifted["observed_at"] = (
    shifted["observed_at"] + pd.Timedelta(hours=hours)
)

# 시각뿐 아니라 관측소도 같아야 값을 가져온다.
result = result.merge(
    shifted,
    on=["station_id", "observed_at"],
    how="left",
    validate="one_to_one",
    sort=False,
)
```

이렇게 하면 09시 행의 1시간 전 값은 08시 관측이 있을 때만 채워진다.
08시가 없으면 결측이고, 07시 값으로 대체하지 않는다.

**② 미래 정답: `attach_targets()`**

```python
# 행 수가 아니라 실제 6시간의 길이를 더해 정답시각을 계산한다.
result["target_at"] = (
    result["observed_at"] + pd.Timedelta(hours=6)
)
```

이후 원본 관측의 시각 열을 조회용 표에서 `target_at`으로 이름만 바꾸고,
`(station_id, target_at)`로 연결했다.
06시 표본은 12시 정답만 가져오며, 12시 행이 없다고 13시를 가져오지 않는다.

실제 코드는 숫자 `6`을 공통 상수 `HORIZON_HOURS`로 사용한다.
위 예시는 시간 계산의 의미를 바로 볼 수 있도록 6을 적은 축약 예다.

**③ 없는 값 처리: `select_complete_samples()`**

```python
missing_features = dataset[list(FEATURE_COLUMNS)].isna().any(axis=1)
missing_target = dataset[TARGET_COLUMN].isna()
excluded = missing_features | missing_target
complete_samples = dataset.loc[~excluded].copy().reset_index(drop=True)
```

자료가 없는 시각을 지어내거나 0으로 바꾸지 않았다.
입력·정답을 만들 수 없는 표본은 이유를 기록해 제외했다.
따라서 이 해결은 **관측 누락을 복구한 것**이 아니라 **관측 누락이 있어도 잘못된 시간 연결을 하지 않도록 한 것**이다.

### 17.6 해결됐다는 것을 어떻게 확인했는가

다음 경우를 코드 테스트로 확인했다.

- 중간 한 시간의 행을 의도적으로 제거해도 이전 행을 1시간 전 값으로 쓰지 않는다.
- 미래 목표시각의 행을 제거하면 정답이 결측으로 남고, 근처 시각 값으로 대체되지 않는다.
- 여러 관측소가 같은 시각을 가져도 다른 관측소의 값을 가져오지 않는다.
- 자정을 넘어도 정확한 시간 차이로 연결한다.
- 미래 관측을 바꾸어도 이전 시점의 입력 특성은 변하지 않는다.
- 불규칙한 관측 간격에서도 학습·검증 경계는 행 수가 아니라 정답시각으로 판단한다.
- 실제 연간 데이터의 과거·미래 값이 독립적인 관측소·시각 조회 결과와 같은지 비교한다.

현재 연간 데이터는 8,043행에서 완전한 표본 5,756행을 선택했고,
분할 경계를 넘는 정답 7행을 더 제외해 최종 5,749행으로 분리했다.
이는 표본 구성 결과이며, 모델 정확도가 향상됐다는 실험 결과는 아니다.

### 17.7 대안과 현재 방식의 한계도 설명하기

**왜 근처 시각의 값을 쓰지 않았는가?**

그렇게 하면 “정확히 6시간 뒤”라는 문제 정의가 달라진다.
근접 시각을 허용하는 문제라면 허용 오차·방향을 명시한 별도 연결 규칙이 필요하지만 현재는 구현하지 않았다.

**왜 모든 시각을 만들고 보간하지 않았는가?**

보간은 가능한 후속 실험이지만 관측하지 않은 값을 추정해서 채우는 선택이다.
특히 미래값까지 참조하는 입력 보간은 예측 시점에 알 수 없던 정보를 사용할 수 있다.
초기 버전은 실제 관측만으로 시간 기준을 명확히 유지하고, 표본 손실을 기록하는 쪽을 선택했다.
미래 정답을 보간해서 실제 관측 정답과 구분 없이 평가하지도 않았다.

**표본을 많이 버린 단점은 없는가?**

있다. 데이터가 줄고 특정 기상 상황이 더 많이 제외되는 선택 편향이 생길 수 있다.
그래서 제외 수와 이유를 남겼으며, 이후 누락 분포·조건별 편향과 대체 처리 방식은 추가 검토해야 한다.

**6시간 대신 임의의 예측 간격도 가능한가?**

시간 기준 연결이라는 원리는 확장할 수 있지만, 현재 시스템 전체는 6시간 예측으로 구현·테스트했다.
상수만 바꾸면 모든 간격을 지원한다고 말하면 안 된다.
정답 열 이름·메타데이터·분할 검사·테스트·모델 학습 조건도 함께 맞춰야 한다.

### 17.8 면접 답변 — 약 30초 핵심형

> 가장 어려웠던 부분은 관측 자료의 시간 간격이 일정하지 않았다는 점입니다.
> 예를 들어 08시 기록이 빠지면 09시의 바로 이전 행은 07시가 되기 때문에, 행 이동으로는 정확한 1시간 전 값을 만들 수 없었습니다.
> 그래서 관측소와 실제 시각을 키로 사용해 정확한 과거값과 6시간 뒤 정답을 연결했습니다.
> 해당 시각의 관측이 없으면 임의로 대체하지 않고 결측으로 남긴 뒤, 제외 이유를 기록했습니다.
> 이를 통해 모델보다 먼저 학습 표본의 시간 기준을 정확하게 만드는 것이 중요하다는 점을 배웠습니다.

말하는 속도에 따라 시간은 달라진다. 먼저 이 핵심형을 자기 말로 설명할 수 있도록 연습한다.

### 17.9 면접 답변 — 약 1분 상세형

> 처음에는 시간 단위 자료이므로 6행 뒤의 파고를 6시간 뒤 정답으로 사용할 수 있다고 생각하기 쉬웠습니다.
> 하지만 실제 CSV를 확인하니 날짜마다 빠진 관측시각이 달랐습니다.
> 실제로 1월 1일에는 08시 행이 없어 06시에서 6행 뒤가 12시가 아니라 13시였습니다.
> 그대로 학습하면 표본마다 예측 시간 간격이 달라져 성능 평가의 의미도 잘못될 수 있었습니다.
>
> 이를 해결하기 위해 행 순서가 아닌 관측소와 시각을 기준으로 연결했습니다.
> 과거 입력은 정확히 1·3·6시간 전 관측을 가져오고, 정답은 기준시각에 6시간을 더한 시각의 실제 관측만 사용했습니다.
> 해당 관측이 없으면 근처 값으로 대체하지 않고 결측으로 유지한 뒤, 입력과 정답이 모두 있는 표본만 선택했습니다.
> 또한 중간 시각을 제거하는 테스트와 실제 연간 자료의 시각별 조회 비교로 연결 로직을 검증했습니다.
>
> 이 과정에서 데이터를 많이 모으는 것뿐 아니라, 모델이 무엇을 언제의 값으로 학습하는지 정확히 정의하는 것이 중요하다는 점을 배웠습니다.

“처음부터 잘못된 방식을 실제 운영했다”는 뜻으로 말할 필요는 없다.
행 이동 방식이 위험함을 발견하고 적절한 방식을 설계한 경험으로 설명하면 된다.

### 17.10 예상 꼬리 질문과 답변 요점

| 질문                                  | 답변 요점                                                                                       |

| 정렬하면 해결되지 않나요?             | 순서는 정리되지만 빠진 시각은 생기지 않으므로 실제 시각 기준 연결이 필요하다.                   |

### 17.11 마지막으로 기억할 한 문장

> 데이터의 빈 시각을 억지로 채운 것이 아니라, 빈 시각이 있어도 다른 시간의 관측을 잘못된 입력이나 정답으로 사용하지 않도록 설계했습니다.
